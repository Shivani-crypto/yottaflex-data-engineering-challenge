1. HIGH-LEVEL ARCHITECTURE & PIPELINE FLOW
================================================================================

The pipeline acts as a data quality gatekeeper between raw incoming orders
and the production analytical database.

Data Flow Diagram:
------------------
[Raw CSV: data/raw/orders.csv]
       |
       v
[Stage 1: Ingestion (ingest_raw_data)]
       |-- Checks file existence & required schema headers
       |-- Catches malformed/corrupted lines -> Routes to Quarantine
       v
[Stage 2: Validation (validate_and_transform_records)]
       |-- Validates order_id presence & intra-batch uniqueness
       |-- Validates customer_id against known customer master list
       |-- Validates order_date format & calendar bounds (is_valid_iso_date)
       |-- Validates amount is non-negative numeric (is_valid_amount)
       |-- Normalizes order_status to lowercase (completed, pending, cancelled)
      / \
     /   \
 [Valid]  [Rejected] --> Appended to data/rejected/rejected_orders.csv
    |
    v
[Stage 3: SQLite Publishing (publish_to_sqlite)]
    |-- Enables PRAGMA foreign_keys = ON;
    |-- Seeds customers reference table
    |-- Identifies existing orders in DB:
    |     * Exact duplicates -> Skipped (Idempotency)
    |     * Conflicting duplicates -> Quarantined
    |     * Brand-new orders -> Inserted inside a single transaction
    v
[Stage 4: File Exports (save_output_csvs)]
    |-- Writes clean orders to data/processed/clean_orders.csv
    |-- Preserves quarantine history in data/rejected/rejected_orders.csv
    v
[Stage 5: History Audit (record_pipeline_run)]
    |-- Inserts execution record into pipeline_runs SQLite table
    v
[Stage 6: Reports Generation]
    |-- reports/quality_report.json (Operational JSON metrics)
    |-- reports/reconciliation_report.txt (Row count reconciliation & SQL)
    |-- reports/performance_report.txt (Throughput & execution timings)

2. main.py - MODULE-BY-MODULE CODE FRAMING
================================================================================

All business logic is contained in main.py using clean, modular functions.
No complex classes or unnecessary decorators are used.

--------------------------------------------------------------------------------
MODULE 1: setup_logger(log_file_path)
--------------------------------------------------------------------------------
Purpose:
  Configures dual-destination logging so operational logs appear live in the
  terminal while simultaneously being appended to a persistent log file.

Inputs:
  - log_file_path (str): e.g., "logs/pipeline.log"

Internal Framing Logic:
  1. Checks if the logs directory exists; creates it if needed (os.makedirs).
  2. Creates a Python logging instance named "EcommercePipeline".
  3. Clears any pre-existing handlers to prevent duplicate log lines.
  4. Attaches a FileHandler (mode="a", encoding="utf-8") to persist logs.
  5. Attaches a StreamHandler (sys.stdout) to display logs in the terminal.
  6. Formats log lines: "%(asctime)s - %(levelname)s - %(message)s".

Output:
  - logger: Configured Python logging object.

--------------------------------------------------------------------------------
MODULE 2: is_valid_iso_date(date_value)
--------------------------------------------------------------------------------
Purpose:
  Validates ISO-8601 calendar dates without relying on slow try/except blocks.
  In high-volume data engineering, defensive string checking is faster and
  completely deterministic.

Inputs:
  - date_value (str): e.g., "2024-05-15", "2024-05-15T14:30:00", "2024-13-45"

Internal Framing Logic:
  1. Strips whitespace and separates optional time part ("T" or space).
  2. If a time part exists, validates hours (00-23), minutes (00-59),
     and seconds (00-59).
  3. Splits date into [year, month, day]:
     - Year must be exactly 4 digits.
     - Month must be 2 digits and between 1 and 12.
     - Day must be between 1 and maximum days in that month.
  4. Leap-Year Handling:
     - Leap year = (year % 4 == 0 and year % 100 != 0) or (year % 400 == 0).
     - February gets 29 days in leap years, 28 days otherwise.

Outputs:
  - Tuple (is_valid: bool, standardized_date: str or None)
    Example: (True, "2024-05-15") or (False, None)

--------------------------------------------------------------------------------
MODULE 3: is_valid_amount(amount_value)
--------------------------------------------------------------------------------
Purpose:
  Validates monetary order amounts using defensive string inspection.
  Prevents invalid values like text, NaN, infinity, or negative numbers.

Inputs:
  - amount_value (str or numeric): e.g., "149.99", "-50.00", "abc", ".50"

Internal Framing Logic:
  1. Rejects None, blank strings, or special text ("nan", "inf", "null").
  2. Rejects negative numbers: amount_str.startswith("-").
  3. Splits string on decimal point '.'. Cannot contain more than 1 dot.
  4. Gracefully supports decimal edge cases:
     - Whole integers: "100" -> 100.00
     - Leading dot: ".50" -> 0.50
     - Trailing dot: "10." -> 10.00
  5. Verifies all other characters are digits (.isdigit()).
  6. Converts to float and rounds to 2 decimal places.

Outputs:
  - Tuple (is_valid: bool, numeric_amount: float or None, error_message: str)
    Example: (True, 149.99, "") or (False, None, "Invalid amount: negative...")

--------------------------------------------------------------------------------
MODULE 4: ingest_raw_data(input_csv_path, run_id, logger)
--------------------------------------------------------------------------------
Purpose:
  Ingests the raw CSV file line-by-line using Python's standard csv module.
  Crucial fix: Unlike pandas on_bad_lines='skip' (which silently throws away
  bad data), this function catches malformed rows, tags them with their exact
  CSV row number, and routes them to quarantine.

Inputs:
  - input_csv_path (str): Path to raw CSV file.
  - run_id (str): Unique run identifier.
  - logger: Logging instance.

Internal Framing Logic:
  1. File Existence: Returns FILE_NOT_FOUND if file does not exist.
  2. Empty File Check: Returns FILE_EMPTY if file is 0 bytes.
  3. Header Check:
     - Reads line 1 using csv.reader.
     - Confirms required columns: order_id, customer_id, order_date,
       amount, order_status.
     - If any required column is missing -> aborts (MISSING_REQUIRED_COLUMNS).
     - If unexpected extra columns exist -> logs warning and continues.
  4. Data Row Iteration (Line 2 onwards):
     - Tracks source_row_number (2, 3, 4...).
     - If row column count != header column count:
       Creates malformed record with line number and reason:
       "Malformed CSV record: expected 5 columns, found <N>"
     - If row has syntax/quoting error:
       Catches exception, records error with line number, continues reading.
     - If row is well-formed:
       Zips with header into dictionary, adds _source_row_number, and
       appends to valid_rows.

Outputs:
  - (header, valid_rows, malformed_records, status, error_msg)

--------------------------------------------------------------------------------
MODULE 5: validate_and_transform_records(raw_rows, source_file,
                                         known_customers, run_id, logger)
--------------------------------------------------------------------------------
Purpose:
  Inspects structurally valid rows against business quality rules and
  separates clean records from quarantined rejections.

Inputs:
  - raw_rows (list of dicts): Structurally sound rows from ingestion.
  - source_file (str): Name of the source file.
  - known_customers (list): Master list of customer IDs (CUST0001 - CUST0100).
  - run_id (str): Run ID.

Internal Framing Logic:
  For each row, establishes a reject_entry template, then validates:
  1. order_id check: Cannot be blank.
  2. Intra-batch deduplication:
     Checks in-memory dict seen_batch_orders. If order_id was already seen
     earlier in this same CSV, the second row is quarantined as:
     "Duplicate order_id within input batch: '<order_id>'"
  3. customer_id check: Cannot be blank; must exist in known_customers.
  4. order_date check: Calls is_valid_iso_date(). Must be valid calendar date.
  5. amount check: Calls is_valid_amount(). Must be numeric >= 0.00.
  6. order_status check: Normalizes to lowercase; must be one of:
     'completed', 'pending', 'cancelled'.
  7. Success: Appends row to valid_records with cleaned date, float amount,
     lowercase status, and processed timestamp.

Outputs:
  - Tuple (valid_records: list, rejected_records: list)

--------------------------------------------------------------------------------
MODULE 6: publish_to_sqlite(valid_records, db_path, known_customers,
                            run_id, logger)
--------------------------------------------------------------------------------
Purpose:
  Publishes valid records into the target SQLite database, enforces relational
  foreign keys, guarantees idempotency on re-runs, and performs atomic commits.

Inputs:
  - valid_records (list): Clean records from validation.
  - db_path (str): Path to SQLite database file.
  - known_customers (list): Valid customer list.
  - run_id (str): Current run ID.

Internal Framing Logic:
  1. Database Connection & Foreign Keys:
     Connects to SQLite and executes: PRAGMA foreign_keys = ON;
  2. Schema Initialization:
     - CREATE TABLE IF NOT EXISTS customers (customer_id TEXT PRIMARY KEY)
     - Seeds customers table with known_customers.
     - CREATE TABLE IF NOT EXISTS orders (
         order_id TEXT PRIMARY KEY,
         customer_id TEXT NOT NULL,
         order_date TEXT NOT NULL,
         amount REAL NOT NULL,
         order_status TEXT NOT NULL,
         source_file TEXT NOT NULL,
         run_id TEXT NOT NULL,
         processed_at TEXT NOT NULL,
         FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
       )
     - CREATE TABLE IF NOT EXISTS pipeline_runs (...)
  3. Pre-Check Existing DB Records (Idempotency Engine):
     Queries existing orders: SELECT order_id, customer_id, order_date, amount
     FROM orders.
     For each incoming valid record:
     - Exact Duplicate: Same order_id, customer, date, and amount.
       Skipped safely. Increments exact_duplicate_count.
     - Conflicting Duplicate: Same order_id, but different details.
       Quarantined. Increments conflicting_duplicate_count.
     - Brand New: Added to records_to_insert list.
  4. Single Atomic Batch Transaction:
     cursor.executemany("INSERT INTO orders (...) VALUES (?, ...)", records_to_insert)
     connection.commit()
     Grouping 100,000 inserts into a single commit reduces disk fsync
     operations from O(N) to O(1), achieving ~40,000 rows/second.
  5. Transaction Rollback:
     If any SQL error occurs, catches exception, executes connection.rollback(),
     and returns db_success: False.

Outputs:
  - Dictionary with counts: pre_run_db_count, post_run_db_count,
    inserted_count, exact_duplicate_count, conflicting_duplicate_count,
    duplicate_rerun_count, db_success.

--------------------------------------------------------------------------------
MODULE 7: record_pipeline_run(db_path, run_data, logger)
--------------------------------------------------------------------------------
Purpose:
  Maintains persistent historical lineage in SQLite. Prevents overwriting
  execution information from previous runs.

Inputs:
  - db_path (str): Database path.
  - run_data (dict): Metrics dictionary for the current run.

Internal Framing Logic:
  Inserts an immutable audit record into pipeline_runs table:
  - run_id (PK), source_file, start_time, end_time, status ('SUCCESS'/'FAILED'),
    input_count, valid_count, rejected_count, inserted_count, duplicate_count,
    failure_reason.

--------------------------------------------------------------------------------
MODULE 8: save_output_csvs(valid_records, rejected_records,
                          processed_csv_path, rejected_csv_path, logger)
--------------------------------------------------------------------------------
Purpose:
  Writes clean and quarantined records to disk.

Internal Framing Logic:
  - clean_orders.csv: Overwritten with the current run's validated orders.
  - rejected_orders.csv:
    Checks if file exists:
    * If new: Writes header and rows.
    * If already exists: Appends new rejected rows without writing header.
    This preserves the complete historical audit trail of all prior rejections.

--------------------------------------------------------------------------------

2. generate_reconciliation_report(reconciliation_data, output_path, logger):

MODULE 10: run_pipeline() & main()

3. generate_data.py - SYNTHETIC GENERATOR CODE FRAMING
================================================================================

Function: generate_orders_dataset(output_path, total_rows=1000, random_seed=42)

Framing Logic:
  1. Reproducibility: random.seed(42) guarantees identical datasets every run.
  2. Generates dates over a 180-day window from 2024-01-01.
  3. Anomaly Probability Engine (random.random()):
     - < 0.02: Injects duplicate order_id from earlier in the batch.
     - < 0.04: Injects missing order_id ("").
     - < 0.06: Injects missing customer_id ("").
     - < 0.08: Injects unknown customer_id ("CUST9xxx").
     - < 0.10: Injects malformed date ("2024-13-45", "invalid-date").
     - < 0.12: Injects missing amount ("").
     - < 0.14: Injects negative amount ("-25.00").
     - < 0.16: Injects zero boundary amount ("0.00").
     - < 0.18: Injects invalid status ("shipped", "refunded").
     - < 0.19: Injects malformed CSV row (6 columns instead of 5).
     - >= 0.19: Generates normal valid order.

5. QUICK REFERENCE & INTERVIEW REVISION CHEATSHEET
================================================================================

Q1: Why did you write simple functions instead of a complex OOP hierarchy?
A1: "For batch ETL pipelines, simple procedural functions with explicit inputs
     and outputs are easier to test, debug, and maintain. They avoid hidden
     state, tightly coupled inheritance, and unnecessary abstraction overhead."

Q2: How does the pipeline ensure idempotency?
A2: "Before inserting, the pipeline queries SQLite for existing order_ids.
     If an order already exists with identical details, it is skipped without
     error. If an order arrives with an existing order_id but altered data,
     it is quarantined as a conflicting duplicate, ensuring target database
     records are never silently overwritten."

Q3: How are malformed CSV rows handled?
A3: "Instead of pandas on_bad_lines='skip'—which silently discards data—we parse
     the file line-by-line using Python's standard csv module. Corrupt lines
     are captured with their source file and line number, and written to
     rejected_orders.csv so that Total Source = Valid + Rejected."

Q4: How did you optimize SQLite insert speed?
A4: "Instead of row-by-row commits, we execute batch inserts using
     cursor.executemany() inside a single transaction. In SQLite, every commit
     triggers an operating system disk sync (fsync). A single commit reduces
     disk syncs from O(N) to O(1), inserting 100,000 records in ~2.5 seconds."

Q5: How does the pipeline handle failure?
A5: "Database publishing runs inside an explicit transaction. If an error
     occurs, connection.rollback() is triggered so zero partial data is
     committed. The failure reason is logged in the pipeline_runs table,
     and retrying the pipeline is completely safe."
